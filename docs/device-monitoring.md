# 設備監控與歷史接續

監控資料由設備持續產生，頁面負責訂閱及查詢。這版提供 3 台固定 ID 的模擬設備，每台預設每秒回報一筆溫度；不需要有人開啟 Streamlit 或 WebSocket。服務停止期間不產生假歷史，也不捏造停機區間的數值。

時間政策：系統使用現行台灣標準時間，所有日期固定 UTC+08:00；不套用歷史夏令時間。資料庫與 API 保留 UTC 時間點。

## 資料流程

| 階段 | 行為 |
|---|---|
| 背景生成 | 單一 lifespan 模擬器每輪產生 3 台設備的資料，預設每輪 1 秒 |
| 批次保存 | 事件進入有界佇列，最多 100 筆或 5 秒提交一次，沿用重試與去重 |
| 即時推送 | 依設備 ID／分類送到訂閱者；沒有訂閱者仍持續保存 |
| 開啟監控 | 先建立設備訂閱，再查詢最近 300 筆已保存資料，合併與排序 |
| 接續更新 | 以事件 ID 去重，每秒更新畫面，約每 5 秒同步最近已保存資料 |
| 查看更早內容 | 按「查看歷史與分析」帶入目前設備，在資料分析選時間範圍並分頁 |
| 暫停與離開 | 僅停止目前畫面的更新／訂閱，後端設備繼續生成；返回或恢復後同步歷史 |

每筆資料保存 `device_id`、`device_name`、`unit`、數值、時間及當下閾值。圖表依設備與分類分隔序列；即使兩台設備使用相同分類，也不應連成同一條線。

## API 與權限

| API | 權限與用途 |
|---|---|
| `GET /api/v1/monitoring/devices` | 任一登入角色；設備清單與模擬設定 |
| `GET /api/v1/monitoring/samples` | 任一登入角色；近期及過往樣本，單頁最多 300 筆 |
| `WS /ws/v1/samples?device_id=device-001` | 任一登入角色；訂閱指定設備的新事件 |
| `GET /api/v1/monitoring/history` | 沿用 Admin 管理歷史入口，單頁最多 100 筆 |
| `GET /api/v1/monitoring/status` | Admin；生成、入庫、佇列及連線狀態 |

介面的同步時間、最新資料時間、告警、圖表與歷史查詢都使用台灣時間（UTC+8）；日期與時間輸入轉成 UTC 後查詢，包含跨台灣午夜的區間。資料庫與 API 的時間點仍保持 UTC，不需要搬移或改寫既有歷史。

樣本 API 支援 `device_id`、`category`、`q`（標題）、`event_id`、`is_anomaly`、`start_time`、`end_time`、`page`、`page_size`。時間需帶時區並轉成 UTC，區間採開始包含、結束不包含；列表按事件時間、資料庫 ID 由新至舊排序，單次查詢的筆數與內容使用同一資料快照。

設備共用工作區，所有登入者皆可在資料分析查看系統設備歷史、聚合分析與 Excel 匯出；系統管理與管線控制維持 Admin 限定。即時歷史分析與 Excel 可使用 `device_id` 篩選，匯出包含設備 ID、名稱與單位。

## 舊資料與可靠性

遷移只增加設備欄位與索引。既有樣本保留原事件 ID、數值、時間及閾值，設備標示為 `legacy`／「舊版未指定設備」，單位留空。設備選單保留舊資料查詢入口，不將舊資料冒充成新設備歷史。

WebSocket 的 `pending` 仍不等於交易已提交；REST 歷史只回傳已提交資料。前端以最近 300 筆定期重新對照，能合併晚提交或短暫斷線時已保存的資料；長時間離開後更早的內容仍在歷史查詢中，不保證全部重播到即時圖表。

資料庫暫時失敗時 writer 會重試，佇列滿載則暫停生成以控制記憶體。突然終止程序可能遺失尚未提交的資料；資料庫 volume 保留的是已提交內容。仍以單一 worker 部署，尚未加入跨程序廣播或持久化訊息通道。
